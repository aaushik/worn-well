# Personal Styling Agent Buildathon MVP Implementation Plan

> **For Hermes:** Execute this plan task-by-task using strict vertical-slice TDD. Keep Hermes session receipts and make real partner integrations visible in the run log.

**Goal:** Ship a public paid personal-styling agent that converts visitors into verified users and customers, uses only garments evidenced in each user's outfit history, returns evidence-backed safe/stretch recommendations, and creates a shareable result that drives the next signup.

**Architecture:** A Cloudflare-hosted React/Vite UI calls Convex mutations/actions. Convex stores wardrobe evidence and run events. A thin Hermes-facing API/tool layer exposes four deterministic operations (`parse_intent`, `search_wardrobe`, `generate_candidates`, `critique_candidates`) coordinated by a Style Director workflow. For buildathon reliability, these are logical specialist stages in one orchestrated workflow—not four independent long-running agents.

**Tech Stack:** TypeScript, React, Vite, Convex, Vitest, Zod, Hermes Agent, Dodo Payments, OpenAI-compatible vision model, ElevenLabs, Cloudflare Pages/Workers. Wispr Flow supplies cleaned text through normal dictation rather than requiring a fragile custom API.

---

## Product and scoring decisions

### Primary and cross-track strategy

**Primary track: Revenue.** The root metric is verified signups, but the product must also collect real product revenue. A signup page alone is not revenue proof. The freemium rule is simple: styling recommendations unlock after **4 outfits**, each user can store up to **10 outfits free**, and attempting to add outfit 11 opens a one-time Dodo checkout for an **Unlimited Wardrobe** unlock. Payments from teammates/friends and consulting fees do not count.

**Cross-track: Virality.** Every completed recommendation produces an optional privacy-safe share card (“My Effortless Coffee-Date Formula”) with a referral link. Shared cards acquire visitors and signups. The same artifact therefore supports distribution without distracting from the Revenue rubric.

The agent workflow remains important product quality and qualifies Hermes usage, but it is not the primary scoring track.

### Handbook constraints to build around

- Hermes must either visibly build the product (session receipts) or be the end-user harness. We will do both where practical.
- The app must be public and usable from a judge's device.
- Proof must be live: Convex tables, agent run events, real outputs, and user feedback.
- Demo format: 20-second context, one happy path, one edge case, then one minute of proof.
- Partner integrations earn only when doing real visible work. Do not add logo-only integrations.
- Revenue, signup, visitor, and referral claims must be visible in live systems and internally consistent.
- Install analytics before distribution; screenshots alone are weak proof.

### Scope corrections

1. **Do not build four autonomous agents.** Four logical specialist stages are enough for a real auditable workflow. Independent agents add latency and failure modes without improving the recommendation.
2. **Wispr Flow is input UX, not backend infrastructure.** Put focus in the request field and dictate with Wispr. Show the cleaned transcript. A custom Wispr API integration is unnecessary unless event docs provide one.
3. **Linkup is optional and late.** Add only if weather/venue context is needed after the core loop works.
4. **Image identity is human-confirmed.** Vision suggests garment records; the user corrects/merges them. Never claim perfect cross-photo recognition.
5. **Safe fallback:** if no valid outfit exists, return an explicit wardrobe-gap result—not invented clothes or shopping advice.
6. **Use progressive value.** At 0–3 outfits, show onboarding progress and basic observations but do not claim wardrobe-grounded recommendations. At 4 outfits, unlock safe/stretch recommendations. Outfits 5–10 improve evidence quality while remaining free.
7. **Do not add subscriptions or packs in the MVP.** Sell one simple one-time Unlimited Wardrobe unlock. It is easier to explain, purchase, verify, and demo.

### Smallest useful data model

- `users`: email, displayName, referralCode, referredBy, wardrobePlan (`free` or `unlimited`), createdAt
- `garments`: userId, label, category, colors[], pattern, fit, silhouette, sourceImageId, status, lastWornAt
- `outfits`: userId, imageStorageId/imageUrl, occasion, moodBefore, confidenceAfter, comfort, liked, disliked, wornAt
- `outfitGarments`: outfitId, garmentId
- `recommendations`: userId, requestText, intent, safeCandidate, stretchCandidate, status, createdAt
- `recommendationFeedback`: recommendationId, accepted, worn, confidence, comfort, notes
- `agentRuns`: userId, requestText, status, startedAt, completedAt
- `agentEvents`: runId, sequence, stage, summary, evidenceIds[], payload, createdAt
- `orders`: userId, provider, providerOrderId, amount, currency, status, productKey (`unlimited_wardrobe`), createdAt, paidAt
- `referrals`: referrerUserId, referredUserId, sourceRecommendationId, createdAt
- `shareCards`: recommendationId, publicSlug, headline, imageUrl, visits, createdAt

Avoid separate preference tables in MVP. Derive evidence from outfit feedback and recommendation feedback.

### Revenue funnel

1. Public landing page: clear promise, sample result, “Create my style profile.”
2. Email signup creates a verifiable Convex user (use real email verification if available; otherwise clearly report unverified signups separately).
3. User sees a wardrobe-readiness meter: 0–3 outfits collects evidence; outfit 4 unlocks recommendations; outfits 5–10 improve recommendation confidence.
4. Attempting to create outfit 11 shows the wardrobe limit and starts checkout for a one-time **Unlimited Wardrobe** unlock.
5. Dodo webhook marks the order paid and changes `wardrobePlan` to `unlimited`.
6. The previously blocked outfit submission can then be retried without losing form data.
7. Dashboard shows visitors → signups → users reaching 10 outfits → checkout starts → paid unlocks → completed recommendations.

Do not call checkout starts or test-mode payments revenue. Demo test mode for reliability, but collect and report only genuine live payments as revenue.

### Ranking

Candidate score (0–100):
- 35 hard-constraint validity (candidate is rejected if any hard constraint fails)
- 20 positive historical evidence
- 15 comfort/confidence evidence
- 10 occasion match
- 10 novelty/recency balance
- 10 requested-vibe match

Negative feedback is a penalty, not a global ban, unless the user phrase is an explicit hard avoidance. A candidate with unsupported garment IDs is rejected before scoring.

## Risks and mitigations

- **No official Wispr API:** use Flow as the keyboard/voice layer; show transcript text.
- **Vision latency/failure:** manual confirmation path is always available.
- **Agent latency:** one orchestrated server action with logical stages; avoid separate agent processes.
- **Hallucinated garments:** structural allowlist validation against retrieved IDs.
- **Sparse history:** return lower confidence or a wardrobe gap; never fabricate evidence.
- **Demo network failure:** seed data locally in Convex, cache approved audio, keep backup recording.
- **Too many integrations:** prioritize Hermes + Convex + Cloudflare; ElevenLabs next; Wispr is input UX; Linkup last.
